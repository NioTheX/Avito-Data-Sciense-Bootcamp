# Классификация ботов — Avito DS Bootcamp

Решение строит признаки по событиям каждой куки внутри её суточного окна и обучает
CatBoost. Основной документ — [solution.ipynb](solution.ipynb): данные, признаки,
конфигурации и цикл экспериментов, проверки, анализ ошибок и создание submission.

## Результат

| Модель | 11–13 апреля | 14–16 апреля | 17–19 апреля, holdout |
|---|---:|---:|---:|
| Random Forest из quickstart | 0.0931 | 0.1047 | 0.1025 |
| Выбранный CatBoost | **0.7568** | **0.7740** | **0.7308** |

Метрика — максимальный Precision среди порогов с Recall ≥ 0.70, рассчитанный
официальным `bot_detection_challenge/metric.py`. На holdout AP = 0.7918,
ROC-AUC = 0.9366. Первая отправка на Stepik получила **0.78780**.

После переноса кода в ноутбук выполнен полный запуск в новом ядре: все 27 кодовых
ячеек завершились без ошибок, метрики всех экспериментов совпали с исходными.
В ноутбуке сохранены рассчитанные таблицы и пять графиков. Итоговый CSV побайтово
совпал с файлом первой отправки; модель и настройки не изменялись.

## Запуск

Исходная проверенная среда: **Python 3.13.14, Windows 10, CPU**, 6 потоков.
Версии библиотек зафиксированы в `requirements.txt`.

1. Положите файлы из архива задания в `bot_detection_challenge/data/`:
   `train.csv`, `test.csv`, `events.csv.gz`.
2. Установите зависимости и откройте JupyterLab из корня проекта.
3. В `solution.ipynb` выберите ядро нужного окружения и выполните
   **Restart Kernel and Run All Cells**.

Пример подготовки окружения в PowerShell:

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
.\.venv\Scripts\python.exe -m jupyterlab
```

Отдельных скриптов запуска, файлов конфигурации и каталога тестов нет.
Все 27 отдельных конфигураций и четыре ансамбля пересчитываются в ноутбуке.
Проверки на маленьких искусственных данных выполняются до обучения моделей.

После запуска появятся:

- `submission.csv` — 4 909 строк, колонки `cookie_id` и `score`;
- `artifacts/experiments/` — конфигурации, метрики и прогнозы текущего запуска;
- остальные файлы в `artifacts/` — аудит, каталог признаков, анализ holdout,
  ошибки, важности и сведения о среде;
- таблицы и графики в выводах ячеек.

Эти файлы создаются заново из исходных данных и исключены из Git.
Сводная таблица всех экспериментов строится из рассчитанных метрик в ноутбуке.
Проверенный полный запуск занял 8,2 минуты; время зависит от машины и нагрузки.
На другой ОС или с другими версиями библиотек последние
цифры прогнозов могут отличаться.

## Данные, признаки и валидация

Train: 11 091 кука, 899 положительных примеров; test: 4 909 других куки.
Разрешены только события `window_start_ts <= event_ts < window_end_ts`.
После фильтрации и удаления полных дубликатов остаётся 283 833 события.
Все 7 928 событий капчи находятся после конца окна и не используются.

События сортируются внутри куки; разные действия с одинаковым временем
сохраняются, но неоднозначные пары не используются в переходах.
Нулевые счётчики отличаются от неопределённых интервалов и отношений: последние
остаются NaN. Признаки вычисляются независимо для каждой куки, без target.

Итоговые **119 признаков**, включая три категориальных, описывают объём и состав
действий, интервалы и сессии, повторяемость ритма, разнообразие объектов, поиск,
семейства User-Agent, платформу, возраст куки и координаты указателя.
Идентификатор куки, абсолютные даты, исходные номера объявлений и тексты запросов
в модель не передаются.

CatBoost: 700 деревьев, глубина 5, learning rate 0.05, L2 = 5, seed 17,
`one_hot_max_size=16`, Logloss. Early stopping и калибровка не используются.
Полная конфигурация явно задана в разделе «Зафиксированное решение».

Для разработки используются 11–13 апреля (обучение до 11-го) и 14–16 апреля
(обучение до 14-го). Конфигурация выбрана до проверки на 17–19 апреля
(обучение до 17-го). Для submission она переобучается на всём train.

## Что повлияло на выбор

- Одних счётчиков недостаточно: временные признаки заметно улучшают baseline.
- Исключение координат из исходной полной модели ухудшает оба отрезка.
- Возраст куки помогает не во всех конфигурациях; он полезен вместе с ритмом
  и one-hot. Полезность группы зависит от остальных признаков и модели.
- Матрица переходов, больше деревьев и веса классов не дали устойчивого улучшения.
- Лучший ансамбль получил среднее 0.7637 против 0.7654 у выбранной одиночной модели.
  Небольшая разница не доказывает статистического превосходства.
- Seed тоже подбирался на разработке, поэтому её оценки оптимистичны;
  отдельный holdout нужен именно для заключительной проверки.

## Ограничения

Разметка описывает известные источники трафика, а не все возможные виды ботов.
Двух недель обучения недостаточно для проверки всех временных сдвигов.
User-Agent можно подменить; координаты зависят от платформы и экрана.
Короткие истории дают мало информации.

Качество по платформам неодинаково: на holdout P@R70 для web — 0.8571,
Android — 0.6230; на iOS только четыре положительных примера.
Bootstrap по кукам даёт примерно [0.638; 0.879], но не моделирует смену источников
трафика и зависимости между куками одного сервиса.

Score не проверен как откалиброванная вероятность. Порог в submission не передаётся.
Перенос порога с предыдущего временного отрезка даёт precision 0.7134 и recall 0.73125 —
это отдельная проверка, не основная метрика.

## Файлы решения

```text
solution.ipynb                    анализ, эксперименты, проверки и итоговый прогноз
src/features.py                   очистка событий и построение признаков
src/modeling.py                   создание моделей, обучение, прогноз и проверка CSV
src/diagnostics.py                пороги, bootstrap и важность групп
bot_detection_challenge/metric.py официальная метрика без изменений
requirements.txt                 версии библиотек
README.md                        описание решения и порядок запуска
.gitignore                       исключение данных, результатов и окружения
```

Модели обучаются локально, внешние API и языковые модели для предсказания
не используются. Ничего автоматически не отправляется и не публикуется.
Допустимость помощи ИИ при разработке следует согласовывать с организаторами
отдельно: отсутствие LLM внутри модели не отвечает на этот вопрос.
